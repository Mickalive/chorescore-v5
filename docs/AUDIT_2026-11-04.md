# Audit produit et automatisation — 4 novembre 2026

Verdict : **produit non prêt ; automatisation précédente improductive**.
Audit des sources V1/V2/V3/V4 consolidées par la matrice cumulée et du produit
V5 ; 34 snapshots rehashés sans divergence. Les conversations privées ChatGPT
ne sont pas une source accessible. La matrice de `VERIFICATION.md` reste la
référence détaillée par exigence ; aucun ancien statut « complete » n’est repris.

## Résultat réel du programme

[Exécution 41535813998](https://github.com/Mickalive/chorescore-v5/actions/runs/41535813998) :
échec après **1 h 17 min 5 s**, trois tentatives, **aucun chemin produit modifié**,
intégration ignorée et HEAD distant resté `9c7cec9`. Les journaux montrent des
appels `task` répétés avec des identifiants invalides (`1`, `task_1`), parfois
une demande de réparation déléguée à `explore`. Le test de lecture de fichier
avait réussi ; il ne démontrait pas une capacité à corriger le produit.

Corrections du contrôleur : délégation désactivée ; consigne d’édition directe ;
arrêt d’un processus sur délégation interdite ou trois erreurs consécutives ;
absence de vérifications coûteuses quand aucun code n’a changé ; sélection
d’un seul problème et lecture des sources pertinentes plutôt que de tout le
journal historique. Le nouveau contrôle préalable exige une source réellement
corrigée : test rouge avant, test inchangé et vert après. **Ce nouveau contrôle
n’est pas encore une réparation produit ni une intégration GitHub démontrée.**

Le journal natif confirme un autre blocage concret : `sdkmanager: command not
found`, avant installation du candidat. Le pilote ajoute désormais le vrai
répertoire `cmdline-tools/.../bin` au PATH ; les deux jobs Android utilisent
Java 21. Le premier échec navigateur provenait d’un bouton de date désactivé ;
les deux essais suivants passaient sans modification du produit. Cette
intermittence n’est pas déclarée corrigée par simple répétition.

Cinq tests Python du contrôleur passent, dont l’arrêt d’un vrai processus
bloqué et le maintien d’une sortie normale. Les tests/specs et l’écriture dans
GitHub restent protégés ; aucune fusion ou publication de production n’est
automatique. Les limites restantes incluent les modifications de dépendances
non autorisées au worker et la reprise après échec sans candidat validé.

## Défauts produit corrigés dans cet audit

- Cache photo HTTP : quatre tests échouaient avant correction. Une présence
  en cache n’autorise plus un autre compte ; lecture sans session et changement
  de compte pendant lecture/téléversement sont refusés. Un HEAD serveur vérifie
  l’ACL et l’existence sans relire/transférer le fichier. Hors ligne, seul le
  compte stable avec appartenance locale persistée peut réutiliser son cache ;
  un refus serveur explicite prévaut. Test avec vrai serveur HTTP/deux bases.
- Jetons Firebase : les transports HTTP refusent les autorités distantes en
  clair, les identifiants dans l’URL et les paramètres d’URL. HTTPS et les
  serveurs HTTP de boucle locale restent permis. Huit tests passent.
- Dépendances : mise à jour compatible de `shell-quote` vers 1.12.0 et de
  `node-forge` vers 1.4.3, sans changer le SDK Expo. L’audit npm initial de l’arbre
  de production signalait 30 vulnérabilités (1 critique, 6 élevées). Il inclut
  aussi des outils de compilation : ce n’est pas la preuve de 30 failles
  exploitables dans l’APK. Les correctifs exigeant un changement de SDK ou un
  décodeur ESM incompatible ne sont pas forcés.
